# Telegram Audio Bot V2 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** rendere affidabile e semplice la trascrizione Telegram, con configurazione browser e tre servizi AI.

**Architecture:** ricostruzione mirata con un servizio di configurazione, revisioni immutabili e due percorsi audio fissi. UI server-rendered; adapter specifici dei servizi; SQLite V2 distinto dalla V1. Le sessioni producono componenti verificabili in sequenza, senza una seconda architettura di fallback.

**Tech Stack:** Python 3.10+, python-telegram-bot, FastAPI/Jinja2, JavaScript leggero, SQLite, FFmpeg, Docker non-root.

**Spec:** [specifica approvata](../specs/2026-10-25-telegram-audio-bot-v2-design.md).

## Global Constraints

- OpenAI, Gemini e OpenRouter; un servizio attivo per volta; entrambi i modelli sullo stesso servizio nel percorso a due passaggi.
- Testo fedele: significato, numeri, negazioni e ripetizioni significative conservati; rimozione esitazioni e correzioni minime.
- Configurazione dal browser; UI scelta “Configurazione e prova”; quattro aree: Panoramica, Trascrizione, Accessi, Diagnostica.
- Non introdurre SPA, Redis, ORM, grafo di pipeline, profili per chat, endpoint arbitrari o fallback tra servizi.
- Non leggere o modificare dati operativi e file riservati; solo fixture sintetiche, percorsi temporanei e client mock durante lo sviluppo.
- Non cambiare deployment, volume o database reali. Non avviare due poller sullo stesso token.
- Secret store obbligatorio; nessun downgrade in chiaro; segreti mai restituiti o registrati.
- Non persistere audio o testo: risultato di prova solo in memoria fino a dieci minuti; ricevuta tecnica nel database.
- Nonce di associazione casuale, hash persistito, monouso, validità dieci minuti; conferma nel browser autenticato.
- Revisioni conservate: attiva, precedente, bozza; credenziali ancora referenziate e lease in corso non rimossi.
- Diagnostica: ultimi 100 esiti per un massimo di sette giorni; solo metadati normalizzati.
- Consegna entro 4.000 caratteri, reply al vocale e topic conservati; cleanup anche su timeout e annullamento.
- UI: testo ordinario con contrasto almeno 4,5:1, tastiera, focus visibile, errori non affidati al solo colore, reduced motion.
- Eseguire una sessione per chat, aggiornare registro e checkbox, committare il lavoro pertinente e fermarsi.

## Review Focus

Questi casi impliciti hanno test assegnati nei piani indicati:

1. Template e testo con parentesi graffe: `{raw_text}` sostituito senza interpretare altro testo come sintassi (S1.2).
2. Risposta AI vuota o fatta di spazi: errore di trascrizione, mai ricevuta riuscita o messaggio vuoto (S2.2).
3. Nonce persistito e riavvio: scadenza basata sul tempo UTC, senza estendere la validità dopo il riavvio (S3.2).
4. Messaggi anonimi, aggiornamenti modificati o duplicati: nessuna chiamata AI non autorizzata o duplicazione parallela (S5.1).
5. Testo AI con HTML, Markdown o ID lunghi: escaping nel browser e testo letterale su Telegram senza overflow (S4.2, S5.1, S7.1).

`audio_model` è il modello multimodale oppure STT secondo la modalità.
`text_model` è obbligatorio solo in `two_stage`; multimodale lo salva come `None`.
`refine_template` deve contenere `{raw_text}`; la sostituzione è letterale.
Il default nuovo `shutdown_seconds=30` è una scelta del piano, non una promessa
di ripresa dopo un crash. Limiti esistenti validi vengono importati in S6.

Usare errori di dominio tipizzati: `RevisionConflict`, `ConfigurationInvalid`,
`TestRequired`, `PrerequisiteMissing`, `ServiceFailure(code, stage, safe_message)`.
Web: conflitti `409`, validazione `422`, assenza auth `401`/redirect login,
CSRF `403`. Nessuna serializzazione generica di eccezioni SDK o credenziali.

Il chiamante possiede il file audio di ingresso e lo elimina in `finally`;
il runner possiede conversioni temporanee, gli adapter gli upload remoti.
Il risultato del runner è uguale per prove browser e uso Telegram.
Il pool mantiene i client per servizio/versione con lease durante le richieste.
Il repository mantiene un conteggio applicativo dei `credential_lease` per
evitare pruning di chiavi ancora usate; non introduce lease persistenti o
un servizio distribuito. Per il catalogo, `for_credential` evita di fabbricare
una configurazione audio solo per leggere i modelli.

Override infrastrutturali: `AUDIO_DIR` (default `audio_files`), `APPLICATION_DB`
(default `<data_dir>/app-v2.sqlite3`), `MASTER_KEY_FILE` (default
`<data_dir>/.master_key-v2`), `WEB_HOST` (`0.0.0.0`), `WEB_PORT` (`8080`),
`WEB_LOG_LEVEL` (`info`), `WEB_SECURE_COOKIE` (`0`). File temporanei soltanto
in `<data_dir>/tmp`. Rifiutare valori porta/cookie non validi; non leggere
variabili dei modelli, prompt o API key. Il segreto di firma sessione web è
generato una volta e persistito cifrato come credenziale `web_session`, con
la sola versione referenziata dal setup state; non una nuova variabile obbligatoria.
Le versioni delle credenziali infrastrutturali si riferiscono con le chiavi
`<credential_owner>_credential_version` (per esempio
`web_session_credential_version` e `telegram_credential_version`). Il pruning
mantiene queste versioni, oltre all'ultima versione conservata per ogni servizio.

## Verifiche e gestione della continuità

Ogni task contiene un ciclo test fallito → implementazione → test riuscito →
commit. Eseguire i comandi con Python dell'ambiente di sviluppo, mai col runtime
reale. Per evitare caricamenti impliciti di `.env` durante la raccolta pytest:

```bash
python - <<'PY'
from unittest.mock import patch
import pytest
with patch('dotenv.load_dotenv', return_value=False):
    raise SystemExit(pytest.main(['-q', '-p', 'no:cacheprovider', 'tests/v2/']))
PY
```

Nei comandi dei singoli task, `python -m pytest ...` indica il test da passare
a questo bootstrap quando nell'ambiente esistono file riservati. Le fixture
devono inoltre isolare ambiente e percorsi prima di costruire servizi.
Non installare nuove librerie per rendere veri test ancora simulati.
Gli SDK esistono già: verificare documentazione ufficiale e versioni supportate
in S2, annotando eventuali aggiornamenti in `requirements.txt` e CONTRIBUTING.

In chiusura aggiornare [registro](../../V2-PROGRESS.md), checkbox e note dei
contratti. Commit piccoli, stage per percorsi espliciti; niente `git add .`.
Se il task richiede un reviewer secondo la skill di esecuzione scelta, la
review e le correzioni precedono il passaggio di sessione.
