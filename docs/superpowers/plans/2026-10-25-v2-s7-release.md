# V2 S7: verifica e consegna — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** verificare i flussi V2, rifinire l'interfaccia e consegnare istruzioni operative attendibili.
**Architecture:** usare le evidenze dei task precedenti, aggiungere scenari completi
e correggere solo problemi osservati. Separare verifiche offline da prove reali dell'operatore.
**Tech Stack:** pytest, browser reale/headless, Docker build isolata, CI Python 3.10–3.12.
**Spec:** [specifica](../specs/2026-10-25-telegram-audio-bot-v2-design.md), sezioni 4 e 12–14.

### Task S7.1: scenari completi e revisione UX/UI

**Files:** creare `tests/v2/test_acceptance.py`; aggiornare test dei bug osservati,
UI, `.github/workflows/ci.yml` e `.dockerignore` se necessario; scrivere
`docs/V2-VALIDATION.md` e completare l'audit UI iniziato in S4.

**Interfaces:** nessun nuovo percorso di esecuzione. TestClient, Telegram simulato
e client SDK mock esercitano gli stessi servizi della produzione.

- [ ] Scrivere `test_empty_install_to_first_voice`, `test_reboot_keeps_acl_and_active_revision`, `test_live_configuration_survives_failed_model_change`, `test_migration_reconfiguration_then_activation`; almeno uno scenario completo multimodale e uno a due passaggi.
- [ ] Mappare tutti i 16 criteri di accettazione della specifica in `V2-VALIDATION.md`, con test/evidenza concreta e indicazione offline/reale. Aggiungere un test solo dove manca una garanzia, evitando duplicati che riscrivano l'implementazione.
- [ ] Eseguire i nuovi scenari: se un bug emerge, riprodurlo prima della correzione. Usare la skill di debugging se richiesta dal problema; modifiche con test significativi, non soltanto screenshot favorevoli.
- [ ] Revisionare nel browser tutte e quattro le aree e setup/login/recupero a 1440×900 e 390×844, tastiera, errori, vuoti, caricamento, successo, nomi lunghi e output con markup. Controllare contrasto 4,5:1, focus, reduced motion e assenza di overflow; correggere la testata mobile pesante dell'anteprima. Usare Impeccable per audit e rifinitura, mantenendo la direzione approvata.
- [ ] Dopo le correzioni eseguire una volta la suite pertinente completa `python -m pytest tests` nel bootstrap sicuro. Verificare se esiste già un esito corrente fornito dall'utente; evitare ripetizioni automatiche senza nuove modifiche. Aggiornare CI per import/suite V2 e confermare dai risultati realmente disponibili la matrice 3.10–3.12, senza attribuire alle prove locali le esecuzioni CI non osservate.
- [ ] Verificare `.dockerignore` prima della build: nessun file riservato, audio, DB o cache nel contesto. Eseguire solo build isolata dell'immagine e controlli non-root; non avviare Compose contro il deployment esistente. Se build/CI/browser non sono disponibili, segnalarli come non eseguiti con motivo.
- [ ] Committare correzioni ed evidenze: `test: verify V2 end-to-end contracts and interface states`.

### Task S7.2: istruzioni, qualità dei modelli e consegna

**Files:** aggiornare `README.md`, `CONTRIBUTING.md`, `AGENTS.md`, `CHANGELOG.md`,
`ROADMAP.md`, `PRODUCT.md`, `DESIGN.md`, `docs/V2-MIGRATION.md`,
`docs/V2-VALIDATION.md` e registro; eventuali metadati Impeccable tramite workflow documentato.

**Interfaces:** nessuna API nuova. README e UI descrivono esclusivamente le
modalità implementate, i protocolli tecnicamente verificati e le misure disponibili.

- [ ] Documentare un avvio locale e Docker, accesso iniziale, associazione proprietario,
  scelta modelli, upload volontario/prova/attivazione, gruppi e problemi comuni.
  Documentare percorsi DB/chiave, backup e rollback; niente comandi contenenti
  token o esempi che richiedano modifiche a file riservati.
- [ ] Aggiornare PRODUCT alla promessa approvata e DESIGN al sistema realmente
  costruito con Impeccable; conservare la storia della roadmap indicando che
  profili multipli, composizione e altre idee V1 sono superate dallo scope V2.
- [ ] Preparare in `V2-VALIDATION.md` un protocollo per l'operatore: audio sintetici
  o autorizzati con numeri, negazioni, nomi, esitazioni, autocorrezioni e rumore;
  confrontare errori rilevanti, latenza e costo disponibile nei servizi/modalità.
  L'operatore usa il browser e le proprie API senza comunicare chiavi o contenuti
  all'assistente. Registrare solo risultati aggregati sicuri e versioni modello.
- [ ] Se tali prove reali sono state eseguite e i risultati sicuri sono disponibili,
  raccomandare scelte in base alle misure. Altrimenti mantenere scelte esplicite,
  distinguere candidati da modelli raccomandati, segnare le integrazioni come
  verificate offline e lasciare il gate di rilascio reale aperto. Non inventare
  qualità, costo, compatibilità attuale o prova in un vero gruppo Telegram.
- [ ] Verificare link, comandi documentati su fixture e differenze finali;
  seguire la skill di verifica prima di dichiarare completamento e quella di
  review per il lavoro complessivo. Correggere i difetti osservati; non avviare
  nuovi redesign o riscritture estranei allo scope.
- [ ] Committare: `docs: document V2 setup migration validation and limits`.
- [ ] Aggiornare registro con stato preciso: sviluppo offline completato,
  prove reali completate oppure ancora da eseguire dall'operatore. Solo con
  evidenze sufficienti dichiarare release pronta; nessun merge, push o deployment
  implicito. Concludere con file, verifiche e azioni esterne residue.
